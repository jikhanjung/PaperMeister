## 읽는 법

- **파일은 고르게 들어가지 않는다.** 서버 큐가 상한(120항목)에 차 있으면 러너는 새 파일을 넣지 않고 기다리고, 자리가 나면 한 틱(5분)에 수십~백여 개를 한꺼번에 넣는다. 그래서 0인 시간 사이에 큰 값이 튄다. 0인 시간은 러너가 멈춘 시간이 아니다.
- 한 시간 최다는 10-05 21시(289), 10-05 02시(227), 10-18 07시(146), 10-07 09시(124), 10-17 02시(119).
- 처리량이 크게 준 기간은 서버 워커가 줄었던 때와 겹친다: 10-14 오후~10-16 오전, 10-17 새벽~10-18 아침, 10-19 03:30 이후(경위는 HANDOFF의 워커 풀 항목).
- 하루 종일 0인 날: 09-28과 10-06은 서버 큐가 줄지 않아 러너가 기다렸다. 09-30 오후부터 10-01 오전까지는 러너를 멈춰 두었다.
- 큰 모노그래프가 많은 컬렉션(Journals and Series)에서는 패널 분할 잡 하나가 40~100항목이라 큐를 오래 차지해, 캡션 요청(= 새 파일 처리)이 몇 시간씩 밀린다(10-18 밤).

## 어떻게 셌나

날짜·시간별 값은 따로 저장되지 않으므로 러너 로그와 진행 상태에서 재구성했다.

1. **처리한 파일 집합**: `<data>/figure_queue.json`에서 끝난 배치는 파일 전부, 진행 중인 배치는 커서 앞까지 (`--status`와 시간별 리포트가 쓰는 규칙과 같다).
2. **시각**: 로그(`<data>/logs/figure_queue*.log`, 09-23부터)의 캡션 요청 줄(`link paper N …`)에서 논문마다 처음 나온 시각. 8,345개 중 7,794개가 여기에 해당한다.
3. **요청 줄이 없는 파일**(도판이 없거나, 다른 컬렉션에서 이미 물어봤거나, OCR이 없는 파일)은 같은 배치에서 바로 앞 파일과 같은 때 넘어간 것으로 본다(커서는 파일 순서대로 걷는다). 앞 파일이 없으면 뒤 파일, 그것도 없으면 배치가 끝난 시각.
4. 한 파일이 여러 배치에 있으면 가장 이른 시각.

**검증**: 10-13부터 시간별 리포트에 찍힌 "처리한 파일" 값 142개와 같은 시각까지의 재구성 누계를 비교하면 차이는 최대 23개, 평균 10개다. 재구성이 약간 많게 나오는 쪽이며, 요청 줄 없는 파일을 앞 파일 시각에 붙이는 규칙 탓이다(실제로는 다음 틱일 수 있다).
