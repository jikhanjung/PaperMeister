# 083 — 502의 정체는 컨테이너 재기동: 재시도 대신 복구를 기다린다

> 구현 기록 (2026-07-28). 선행: [075](./20260727_075_Qwen_5xx_Transient_Retry.md)에서 넣은
> 5xx 재시도가 **실전에서 한 번도 성공하지 못했음**이 로그로 드러났고, 사용자가 원인을 알려줬다.

## 측정이 먼저였다

앱 재기동 + 77편 복구 후 하루치 로그(`biblio_20260728.log`, 2,969행) 실측:

| 지표 | 값 |
|---|---|
| 시도한 논문 | 179편 |
| PARTIAL | **4편 (2.2%)** — timeout 3 / bad JSON 1 |
| `no_array` · `empty_result` | **0건** (079의 가드들이 오탐 없이 조용함) |
| 5xx | 502 × 60, 500 × 12 |

5xx는 **밤사이에 집중**: 00시 18 / 01시 6 / 03시 18 / 04시 12 / 05시 6 / 07시 12,
**08시 이후 0건**.

**자정 롤오버 실전 확인** — 7/27 로그가 23:59에 끝나고 새 파일이 열렸다.

## 결정적 숫자: 72 / 24 = 정확히 3:1

재시도 발동 72회, 최종 실패 24회. `server_retries=2`이므로 실패 1건당 경고 2줄 + 에러 1줄
= 3:1. 즉 **24건이 예외 없이 전부 재시도 2회(5s+15s)를 다 쓰고 실패**했다.
**성공률 0%.**

우연이 아니었다. 사용자 확인:

> "502 에러는 컨테이너가 죽었다가 다시 뜨는 거라서 시간이 좀 걸려."

컨테이너 재기동 + 모델 로드는 **분 단위**다. 20초 backoff로는 **구조적으로 불가능**했다.
075에서 "짧은 blip을 흡수한다"고 설계했는데, 이 배포 환경에는 그런 blip이 애초에 없었다.

## 진짜 손해는 낭비된 20초가 아니었다

502가 나면 `HTTPError`가 `extract_references_llm` **밖으로** 나간다. 그러면 그 논문에서
**이미 파싱해둔 배치들이 전부 버려진다**. 116엔트리짜리 논문이 마지막 배치에서 502를 만나면
거의 전부를 다시 해야 한다. 낭비된 20초보다 이쪽이 훨씬 크다.

## 수정: 재시도가 아니라 복구 대기

502는 애매한 신호가 아니다. **프록시는 살아서 "뒤에 아무도 없다"고 명시적으로 답하는 것**
이다. 재시도할 게 아니라 기다릴 일이다.

- **게이트웨이 계열(502/503/504)** → in-place 재시도 **제외**. 대신 `_wait_for_server`가
  엔드포인트를 **15초 간격으로 폴링**하다가 살아나면 **같은 배치를 이어서** 한다
- **500은 짧은 재시도 유지** — `EngineCore encountered an issue`는 프로세스가 살아있는
  상태의 오류일 수 있어 컨테이너가 사라진 것과 성질이 다르다
- **상한 900초** (`refs_recovery_wait` pref) — 영영 안 돌아오는 서버는 그때 예외로 올려
  `ServerGuard`가 큐를 pause하도록 넘긴다. 대기가 무한정 매달리지 않는다

워커 스레드에서 기다리므로 UI는 안 멈춘다. **OCR 워커가 이미 같은 인라인 폴링 방식**을 쓰고
있어(devlog 070) 관례도 일치한다.

### 감수한 비용

대기 중에는 **Cancel이 즉시 반응하지 않는다**(대기가 끝나야 적용). 상한이 그 한계를 막는다.
취소 콜백을 배선하는 대안도 있지만, 현재 Cancel 정책이 이미 "진행 중 1편은 마무리"라
성격이 크게 어긋나지 않아 상한으로 갈음했다.

### 계층 정리

| 층 | 담당 | 시간 규모 |
|---|---|---|
| `_call_qwen` 재시도 | 500 같은 순간적 오류 | 초 |
| **`_wait_for_server`** | **컨테이너 재기동** | **분** |
| `ServerGuard` pause/poll | 서버가 오래 죽어있음 | 분~시간 |

가운데 층이 비어 있었다. 그래서 분 단위 장애가 초 단위 재시도에 부딪히고 논문을 잃었다.

## 곁들여: `ServerGuard` 로깅

로그를 읽다가 "이 배치가 밤사이 멈췄던 적이 있나?"를 **알 수 없다**는 걸 발견했다.
`ServerGuard`에 로깅이 전혀 없고 UI 콜백만 부른다. 무인으로 도는 큐에서 가장 알고 싶은
정보인데 기록이 없었다.

`biblio` 로거로 남기도록 추가 — 어떤 임계값이 걸렸는지, 큐에 몇 개가 남아 있었는지,
**복구까지 얼마나 걸렸는지**(`2h 2m` 형태). blip으로 판정해 계속 간 경우도 남긴다. 그래야
"3번 실패했지만 계속 감"과 "3번 실패했는데 아무도 눈치 못 챔"이 로그에서 구분된다.

## 검증

기존 재시도 테스트 3건이 **의도적으로 깨졌다** — 502를 재시도한다는 전제로 쓰였기 때문.
새 계약으로 갱신했다. 추가 테스트:

- 502 → 복구 대기 → **같은 배치 재개**, 스킵 0, 레퍼런스 전부 보존
- 복구 안 되면 예외로 올라감(guard가 받도록)
- 502/503/504가 **backoff를 전혀 안 씀**(sleep이 호출되면 실패하도록 고정)
- guard의 pause/resume이 로그에 남고 지속시간이 사람이 읽을 형태로 찍힘

`ruff`·`mypy` clean, **127 passed**.

근본 원인(엔진이 왜 죽는가 — OOM 유력)은 여전히 서버 측이며, 우리 쪽 대응은 봉쇄까지가 한계다.
